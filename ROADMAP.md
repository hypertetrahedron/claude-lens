| File-history recovery for subagent edits | Complete | A subagent's transcript records Edit/Write calls but no `toolUseResult`, so 110 edits on this machine produced no rows at all. `~/.claude/file-history/<session-id>/<hash>@v<N>` holds full copies of each checkpointed version, and `<hash>` is `sha256(absolute path)[:16]` - verified, which is what makes a version file attributable to a path at all, since `backupFileName` is usually null on the `file-history-delta` entry and only reliably present in a `file-history-snapshot`'s `trackedFileBackups`. Consecutive versions are diffed with `difflib` into `edits` rows with `source='file-history'`, only for sessions with unmeasured subagent edits and only for files that session has no `edits` row for. **Limits:** only the newest version or two of a file survives, so the first change to a file usually has no earlier version to diff against; a run of edits between two checkpoints is recovered as one net change attributed to the prompt open at the later checkpoint; and attribution is to a prompt, never to a `tool_use_id`, so per-tool-call attribution stays out of reach. | Ingest cost of the v8 columns | Complete | A full forced re-parse of the 30x tree went 2.87s -> 4.91s when v8 landed; it is now 4.69s. The cause was measured rather than assumed, and the obvious suspect was wrong: decoding `tool_result` lines for their sizes costs 0.41s in situ, not the ~2s supposed. The rest is spread thin across genuinely new work - input serialisation ~0.2s, ten more usage fields per request ~0.15s, and session events, agents, injected prompts, compaction checks, per-transcript commits and `idx_req_ts` making up the remainder. | Cache-miss classification | Complete | For consecutive main-conversation requests in a session, a request is a miss when its cache writes are more than half its input and the request before it read from the cache - a warm cache that was not used. The cause is the first that fits: `model_switch`, `effort_switch`, `speed_switch`, `compact` (an event between the two), `idle_gap` (past the 60-minute TTL for the main conversation on the Anthropic API, 5 minutes otherwise), else `unknown`. `miss_cost` is that request's cache-write tokens at its own rate. On this machine one session shows a single miss, caused by an idle gap, costing $0.57 - which is the point: it is a real number attached to a real cause. |
| Context series | Complete | One point per main-conversation request carrying `context_tokens`, cache reads and writes, the model, and any `compact` / `model_switch` / `effort_switch` event that landed since the previous request. Subagent requests are excluded - they run against their own context, so mixing them in draws a sawtooth that never happened. Capped at 200,000 points, dropping whole sessions oldest-first, with the cap stated in `notices`. |
| Payload size at scale | Complete | The context series is one point per API request and was two thirds of the payload: the 30x tree's `dashboard.html` went 357 KB -> 1.49 MB. Three encodings brought it back to 964 KB: `t` delta-encoded against a base, `session` and `model` run-length encoded as `[first index, value]` pairs, and `miss` / `cause` / `event` sparse, since they are empty on 99% of points. `rehydrateCtx()` in the template undoes all three, so nothing downstream knows. Build time at 30x went 0.26s -> 0.69s: two ordered per-request passes over 38k rows (the context series, and the 5-hour blocks) are the whole of it and neither can be a GROUP BY, since both depend on what the previous request did. What was recoverable was recovered - the block scan resolves one Rate per (model, provider, speed, region, day) instead of one per request, takes its rows already ordered from `idx_req_ts` rather than sorting them in Python, and keeps only the last half hour of requests for the burn rate instead of the whole month. Real data: 0.29s writing 23 conversation pages, 0.12s when none of them moved. |

| Session and block tables | Complete | `sessions` rows carry the span, prompts, calls, cost, tokens, cache hit fraction, models, model switches, dominant effort, compactions, peak context, cache misses and their cost, the subagent cache TTL and the first prompt's text. `blocks` are ccusage-style 5-hour billing blocks over the last 30 days with a `burn` rate (tokens and dollars per minute over the last half hour) and a projected cost at block end for the open one. |

| Build test suite | Complete | `test_build.py`: 32 tests over a temporary database built through `db.py`'s own insert functions - streamed-duplicate correction, task-notification folding, the new row fields, fast-mode pricing, tool attribution summing to the input-side cost, every named cache-miss cause, the context series and its cap, the compressed wire form round-tripping through a Python copy of `rehydrateCtx()`, 5-hour blocks and burn, the whole payload parsing with every old key still present, conversation pages including a `<script>` in a prompt coming out escaped and a rerun writing nothing, and the digest's week-over-week output. |
| Tool cost attribution | Complete | `tool_attrib` shares a turn's input-side cost (cache read + cache write + uncached input) out across its tools in proportion to result bytes, because a tool result enters the context once and is then re-read on every later request of the turn. It is a share-out, not a measurement: the totals are exact and the split is an attribution, which is what the README says beside it. A tool whose result size was never recorded falls back to its share of the call count. |

## Deferred

- **Claude Chat usage** — conversations live server-side; the desktop app
  keeps no local per-conversation or token record (Local Storage and IndexedDB
  hold auth/UI state only, and the HTTP cache carries no accounting). The one
  local signal, `plan-usage-history.json`, is account-wide and cannot be split
  by product or conversation, so it cannot answer "what did Chat cost". It is
  now charted for what it *can* answer — see the plan-limit gauges above —
  but per-conversation Chat accounting stays out of reach.
- **Bedrock cost verification against a live account** — the Bedrock and
  Vertex rate tables default to Anthropic list prices, and provider behaviour
  (whether Claude Code reports `cost_usd` over OTel on Bedrock, whether the 1h
  cache tier exists there) has not been checked against a real deployment. The
  override file exists precisely because these are assumptions. Would be
  unblocked by access to an account on either route.
- **Provisioned Throughput and batch billing** — both break the per-token
  model entirely (hourly commitment; ~50% discount). Nothing here can estimate
  them; reconciling against AWS Cost Explorer or the CUR would be the real
  answer.
- **Receiver restarting itself on a code change** — tried twice and rejected.
  Exiting with a non-zero code did not make Windows Task Scheduler restart the
  task, and `os.execv` left nothing listening at all. Stopping rebuilds and
  logging is the safe half; a supervisor that genuinely restarts (systemd
  `Restart=on-failure`) could take the stricter behaviour later.
- **Windows remotes over SSH** — the collector assumes a POSIX remote (`sh`,
  `find`, `tar`). Supporting Windows would need a second, PowerShell-based
  collection path and a way to detect which to send. Workaround today: share
  the machine's `.claude` folder and point `--extra-dir` at it. Would be
  unblocked by demand for it plus a Windows host to test against.
- **Pre-2.1.168 transcript layouts** — format handling is derived from real
  transcripts written by CLI 2.1.168 through 2.1.240. Nothing in the ingester
  assumes a version, so older layouts may well parse, but there is no data on
  hand to confirm it. Would be unblocked by a sample of a genuinely old
  `~/.claude` tree.
- **Live telemetry from remote machines** — remote rows are only as fresh as
  the last fetch. True live coverage would mean running a receiver per machine
  and merging, or exposing this receiver beyond localhost, which the current
  "prompt text never leaves the machine" guarantee rules out.
