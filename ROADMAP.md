# Roadmap

Status legend: Not Started · In Progress · Complete · Deferred
Last updated: 2026-09-08

| Feature | Status | Notes |
|---|---|---|
| One home for the query_source vocabulary | Complete | `MAIN_QUERY_SOURCES`/`MAIN_QS_SQL` moved to `db.py` so `jsonl_ingest.py` stops carrying its own copy of the same pair as a SQL literal, and `SUBAGENT_QS_SQL` joins them: the transcript writes `subagent`, OTel writes `agent:builtin:<type>`, and the bare literal at the subagent cache-TTL query was keeping only the 600 rows OTel never saw while dropping 453 it did. There is deliberately no tuple of subagent literals - OTel's spelling carries the type inside the value, so `is_subagent_qs()` is the Python-side twin instead of a list that would invite the `IN (...)` this exists to prevent. |
| Ingest survives a transcript it cannot parse | Complete | `ingest_tree()` guarded only its `os.stat`, so one file written by a newer CLI aborted the whole run - every later transcript in every source, plus Cowork and session titles - and the receiver re-failed on it hourly forever. Failures are now counted per file, rolled back, named in the log and surfaced in `run()`'s result. Connections in `run()`, `remote_status()` and `build()` close on every path; each leaked one held a WAL read mark that blocked checkpointing. |
| Cost figures say what they are | Complete | A session repriced from the CLI's own `total_cost_usd` no longer marks its prompts exact: the CLI measured the session, each prompt holds that total scaled by its own estimate, and the notice bar now says so. Repricing is also refused outright when any prompt in the session ran an unpriced model - such a prompt costs $0.00, so it carried no weight in the split, handed its share to its neighbours and then displayed as a measured zero. Per-prompt `peak_ctx` gained the main-conversation filter its per-session twin always had; on real data 96 of 533 prompts were reporting a subagent's context window as the main thread's, the worst three at 410k, 345k and 291k tokens. `agent_spans()` honours `since` for its `agents` query, which `digest.py` passes. |
| Query and ingest performance | Complete | `connect()` sets `cache_size=-20000` and `mmap_size=256MB` (the latter guarded, since it may raise) against a >10MB working set that `collect()` scans four or five times per rebuild. `recover_file_history()` was four queries per session plus one `execute()` per recovered diff, running hourly inside the lock live telemetry needs; the reads are now chunked `IN (...)` batches following `conversations.py`'s pattern and the writes are one `insert_edits()`. Equivalence checked row-for-row against the pre-refactor code over the real transcript tree and a six-session harness covering every skip branch. |
| Receiver and output hardening | Complete | The single-instance guard now works on Windows: `allow_reuse_address` is off there and `SO_EXCLUSIVEADDRUSE` is set before bind, because SO_REUSEADDR *permits* rebinding a live port on Windows - two scheduled-task receivers could both ingest and both rebuild. `do_POST` gains a 30s socket timeout, a 32MB `Content-Length` cap and incremental gzip decompression, and rejects any request carrying an `Origin` header or a non-JSON content type: a cross-origin `fetch` with a plain-text body is a CORS simple request, so a page the user merely had open could POST fabricated telemetry to localhost and land prompt text in the dashboard. Every rejection is logged rather than silent. `conversations.py` and `report_index.py` write through `tempfile.mkstemp` instead of a fixed `.tmp` name, which two concurrent writers could interleave. Verified: a second bind raises WinError 10048, a 64MB declared body and a gzip bomb both return 413, `text/plain` returns 415, and two threads writing 500KB concurrently produce one whole file. |
| Schema v9: agent_name and cache-TTL repair | Complete | Live telemetry had been writing the subagent *type* into `agent_name`, where a transcript writes the CLI's agentId - the only value that joins `agents`. On this machine that left 453 OTel rows holding 3 distinct names against 36 real ids, collapsing every subagent span in a session into one bar spanning first to last request. `agent_name` now fills rather than replaces, the receiver stops sending the type (`query_source` already carries it), and `_migrate_to_9` clears the type-valued rows so a re-parse restores the id. The same migration resets 2,258 OTel rows (10.1M cache-write tokens) whose 5m/1h split was stored as `0`/`0` - a value `COALESCE` keeps, so no re-parse could correct it and the writes billed at the unsplit 1h multiplier. `REQUEST_SQL_JSONL_FILL` gains the raise-never-lower guard its sibling always had. Verified against a copy of the live DB: totals unmoved, 600 transcript agentIds and 583 joins preserved, fresh and migrated schemas column-identical. |
| Additional local `.claude*` directories | Complete | Siblings of the primary dir are discovered and ingested; projects prefixed with the folder name. Siblings are searched to the same depth as extra locations, so a container like `~/.claude-archive/oldbox/.claude` resolves too. Covered by `test_sources.py`. |
| Deep search of candidate locations | Complete | `--extra-dir` paths are searched to `--depth` levels (default 4) for anything Claude-shaped, so a path above the real dir still works. Recognises renamed/copied dirs by their transcripts. |
| Remote collection over SSH | Complete | One `sh`/`find`/`tar` call per host into `remote-cache/<host>/`, incremental by mtime, failures contained per host. Verified live against a LAN host on 2026-08-22: 21 transcripts pulled, 14 sessions ingested under the host's label; re-run transferred 0 files in 0.3s; an unresolvable host returned a clean error without aborting the build. |

Verified live: dead host costs 8s once then 0.3s per pass, working host unaffected. |

| Live capture of effort, speed and context size | Complete | The receiver stores `effort`, `speed`, `cost_usd`/`cost_usd_micros`, `duration_ms` and `context_tokens` (input + cache read + cache write) from `claude_code.api_request`, per the documented OTel attributes. `check_live.py` prints the fill rate of each so "the CLI is too old for this attribute" is distinguishable from "the receiver is not running". `effort` and `speed` are fill-only on an OTel upsert, like the cache TTL split before them: the receiver reads both from event attributes that some events omit, and replacing rather than filling turned a measured high/fast into NULL the moment live telemetry caught up with a transcript row. And because live mode writes the OTel row first, filling is not enough on its own: `REQUEST_SQL_JSONL_FILL` lets a later transcript COALESCE the transcript-only columns onto a row already marked `otel`, so `--force` repairs history the receiver claimed before the transcript was read. | API errors are recorded, not lost | Complete | `claude_code.api_error` writes an `api_requests` row with `error` = `"<status_code>: <message>"` and zero tokens. Rows are keyed on `request_id` falling back to `client_request_id` - the server id is absent on timeouts and connection failures, and a NULL primary key is legal in SQLite, so without the fallback a flaky network filled the table with unjoinable rows. An error never overwrites a successful row: a retried attempt can share an id, so an existing row only gains the error text. |

| File-history recovery for subagent edits | Complete | A subagent's transcript records Edit/Write calls but no `toolUseResult`, so 110 edits on this machine produced no rows at all. `~/.claude/file-history/<session-id>/<hash>@v<N>` holds full copies of each checkpointed version. Which backup belongs to which file is taken from the transcript's own `backupFileName` wherever it gives one - that is the name on disk, so nothing has to be guessed about the string the CLI hashed - with `sha256(absolute path)[:16]` as the fallback for older transcripts that record no name. Consecutive versions are diffed with `difflib` into `edits` rows with `source='file-history'`, keyed by the backup's own filename so a second pass collides with itself, only for sessions with unmeasured subagent edits and only for files that session has no `edits` row for. **Corrected after checking real transcripts:** the first cut assumed the tracked path was absolute and joined it with `os.path.join`, which was wrong three ways - `realParentDir` is null on every snapshot seen, the tracked key is relative to the session `cwd` and keeps its subdirectories rather than being a basename, and joining a POSIX path with `ntpath` splices a backslash into the very string the hash is taken over. Every lookup missed and recovery silently wrote nothing; `join_tracked` now joins in the flavour the path was recorded in, and the absolute path comes from `sessions.cwd`. **Limits:** only the newest version or two of a file survives, so the first change to a file usually has no earlier version to diff against; a run of edits between two checkpoints is recovered as one net change attributed to the prompt open at the later checkpoint; and attribution is to a prompt, never to a `tool_use_id`. On this machine the two conditions still never coincide in one session, so recovery writes 0 rows here - `FileHistoryRealShape` covers the real snapshot shape (relative key, null parent, named backups) and `FileHistoryPathShapes` the joining, including reproducing a backup name seen on disk. **And one the fix itself caused, caught against real data:** with lookups working, the pass immediately double-counted two edits this repository had already measured. `realParentDir` here is the UNC target of a mapped drive, so the recovered path spelled the same file differently from the tool call's `y:\...` and the "already measured" guard compared strings. It now compares `_path_key` - the lowercased basename - which sees through drive versus UNC and case; matching too broadly only skips a recovery, which is already a documented limit, where a double count is a wrong number. |

| Ingest cost of the v8 columns | Complete | A full forced re-parse of the 30x tree went 2.87s -> 4.91s when v8 landed; it is now 4.69s. The cause was measured rather than assumed, and the obvious suspect was wrong: decoding `tool_result` lines for their sizes costs 0.41s in situ, not the ~2s supposed. The rest is spread thin across genuinely new work - input serialisation ~0.2s, ten more usage fields per request ~0.15s, and session events, agents, injected prompts, compaction checks, per-transcript commits and `idx_req_ts` making up the remainder. Recovered what was recoverable without losing data: `relevant()` now bounds its scan with `find(key, 0, 4096)` instead of copying a 4 KB slice per line (net faster than the v7 filter it replaced), one JSON encoder is built at import instead of one per tool call, a repeated content block of an already-buffered request no longer rebuilds its tuple, and a user entry with no `toolUseResult` skips two calls. ## Deferred

- **Claude Chat usage** — conversations live server-side; the desktop app
  keeps no local per-conversation or token record (Local Storage and IndexedDB
  hold auth/UI state only, and the HTTP cache carries no accounting). The one
  local signal, `plan-usage-history.json`, is account-wide and cannot be split
  by product or conversation, so it cannot answer "what did Chat cost". It is
  now charted for what it *can* answer — see the plan-limit gauges above —
  but per-conversation Chat accounting stays out of reach.
- **Bedrock cost verification against a live account** — the Bedrock and
  Vertex rate tables default to Anthropic list prices, and provider behaviour
  (whether Claude Code reports `cost_usd` over OTel on Bedrock, whether the 1h
  cache tier exists there) has not been checked against a real deployment. The
  override file exists precisely because these are assumptions. Would be
  unblocked by access to an account on either route.
- **Provisioned Throughput and batch billing** — both break the per-token
  model entirely (hourly commitment; ~50% discount). Nothing here can estimate
  them; reconciling against AWS Cost Explorer or the CUR would be the real
  answer.
- **Receiver restarting itself on a code change** — tried twice and rejected.
  Exiting with a non-zero code did not make Windows Task Scheduler restart the
  task, and `os.execv` left nothing listening at all. Stopping rebuilds and
  logging is the safe half; a supervisor that genuinely restarts (systemd
  `Restart=on-failure`) could take the stricter behaviour later.
- **Windows remotes over SSH** — the collector assumes a POSIX remote (`sh`,
  `find`, `tar`). Supporting Windows would need a second, PowerShell-based
  collection path and a way to detect which to send. Workaround today: share
  the machine's `.claude` folder and point `--extra-dir` at it. Would be
  unblocked by demand for it plus a Windows host to test against.
- **Pre-2.1.168 transcript layouts** — format handling is derived from real
  transcripts written by CLI 2.1.168 through 2.1.240. Nothing in the ingester
  assumes a version, so older layouts may well parse, but there is no data on
  hand to confirm it. Would be unblocked by a sample of a genuinely old
  `~/.claude` tree.
- **Live telemetry from remote machines** — remote rows are only as fresh as
  the last fetch. True live coverage would mean running a receiver per machine
  and merging, or exposing this receiver beyond localhost, which the current
  "prompt text never leaves the machine" guarantee rules out.
